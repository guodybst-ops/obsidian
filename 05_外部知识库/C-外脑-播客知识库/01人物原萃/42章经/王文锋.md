# 王文锋

## 画像

- **身份**：Sheet0 创始人
- **背景**：程序员出身的创业者，做 Agent 已有两年。聚焦 Data Agent——将非结构化数据收集清洗为结构化表格，再做定量分析和行动
- **标签**：Agent / Context Engineering / 环境反馈 / 垂直 Agent / 结构化输出

## 擅长 & 不擅长

- **擅长**：从 RL 视角理解 Agent 产品设计——如何定义环境、action 空间和 reward 信号；Context Engineering——如何自动获取、筛选、校验和更新信息
- **不擅长**：模型训练和算法研究（他的能力在 Agent 工程而非底层模型）；消费级产品的 UI/UX（他的产品是表格 Agent，面向数据需求而非视觉体验）。数据不足——仅一集，全面能力无法判断

## 核心心智模型

### 模型1：Agent = 模型 + 环境反馈 + 工具调用

- **一句话**：Agent 是模型基于环境反馈去使用工具的程序。与普通大模型应用的核心差异是在执行中不断获取反馈并调整下一步行动
- **来源**：[[42章经]] 040 [原话/归纳]
- **怎么用**：
  1. 设计 Agent 产品时先定义三要素：状态（context——当前知道什么）、行动（工具调用——能做什么）、奖励信号（反馈——怎么判断做对了）
  2. 把产品变成环境：反馈机制是 Agent 公司的核心差异——单靠 prompt 让模型自己评价自己容易陷入循环
  3. 结构化输出更适合做反馈载体：表格中的空值、错误字段、缺失行一目了然——比自然语言更容易验证
- **局限性**：他的 RL 视角来自学术训练——把一切都建模为 environment-state-action-reward 虽然精妙，但不是所有产品都便于这样定义。很多 Agent 产品的「反馈」是滞后的（用户几天后才给 NPS），RL 最核心的「即时 reward」在大多数产品中不存在

### 模型2：垂直 Agent > 通用 Agent

- **一句话**：垂直 Agent 长期优于通用 Agent——因为垂直场景更容易定义环境、行动空间和结果标准。越通用，方法越泛化，随机性也越高
- **来源**：[[42章经]] 040 [归纳]
- **怎么用**：
  1. 设计 Agent 时先问：我的场景能不能明确定义「什么是对、什么是错」？
  2. 能明确定义的 → 垂直 Agent（如数据收集→结构化→校验）
  3. 不能明确定义的 → 不适合 Agent 模式，或需要更长 R&D 周期
  4. 垂直 Agent 的价值锚定：不是「多种场景通用」，而是「这个场景里最可靠」
- **局限性**：垂直场景市场较小——「数据收集→表格」这个场景能支撑多大的公司？他的逻辑上正确但商业上可能天花板有限。而且「垂直 Agent 更好」是在 Agent 能力受限的前提下的结论——如果模型能力发生质变，通用 Agent 的上限提高就可能改变这个权衡

### 模型3：Context Engineering——Agent 的隐形竞争力

- **一句话**：Agent 的进展不只来自模型，也来自 Context 工程——如何自动获取、筛选、校验和更新信息。用户交互的自由度比准确度更关键
- **来源**：[[42章经]] 040 [归纳]
- **怎么用**：
  1. 设计 Agent 时除了关注模型能力，还要关注「context 的获取和维管」——信息怎么自动流入？怎么校验？过期了怎么办？
  2. 聊天框是最重要入口——因为它最大化用户表达自由度（用户不需要适应 UI）
  3. 结构化输出（如表格）比自然语言更适合作为 Agent 产品的基本交付——因为可验证
  4. 越强大 Agent，用户越不用动脑——降低认知负担
- **局限性**：Context Engineering 高度依赖于数据接入的成本和质量——如果你的用户数据主要在 Slack、PDF 扫描件、会议录音中，自动「筛选和校验」的工程难度指数级上升。这个框架更适合有固定数据格式的垂直场景

## 决策启发式

1. **Agent 是模型基于环境反馈去使用工具的程序**——核心差异是有执行中的反馈回路，不是一次生成 — [[42章经]] 040
2. **你如何把产品变成一个环境，是 Agent 创业公司非常关键的问题** — [[42章经]] 040
3. **越通用，越泛化，随机性越高**——垂直 Agent 更好不是因为聪明，是因为环境能定义 — [[42章经]] 040
4. **大模型输入可以非结构化，但输出最好是结构化的**——结构化才能被校验 — [[42章经]] 040
5. **用户交互的自由度比准确度更关键**——不要让用户适应 UI，让 Agent 适应用户 — [[42章经]] 040
6. **AI Coding 是大模型的灵巧手，也是 Agent 的强工具**——但应优先复用现有可靠工具，没有时才退化为生成代码 — [[42章经]] 040

## 内在张力 / 盲区

1. **RL 框架的过度拟合风险**：他用 RL 视角理解一切——把产品定义为 environment state action reward——虽然自洽，但这可能简化了产品设计的复杂度。用户的真实反馈往往不是「reward signal」而是「模糊的失望」或「无法描述的体验差」
2. **非 AI Coding Agent 的能力边界**：他谈到 AI Coding 是 Agent 的强工具——这更像个人的技术偏好而不是普适原则。非技术用户的产品中，AI Coding 几乎没有用武之地——他和张海龙一样被开发者视角局限
3. **表格 Agent 的商业天花板**：他选择了「数据收集→结构化表格」作为产品方向。这是一个明确可以定义为 environment-reward 的场景——但也因此天花板可能很低
