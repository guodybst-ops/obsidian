# 路宇

## 画像

- **身份**：Dify.AI 创始人兼 CEO
- **背景**：做了五六年 DevOps/开发者工具，2023 年初创立 Dify（最早叫 AI Trainer），定位 LLMOps 中间层平台。开源一周 3000 GitHub stars，半年内 12000+ stars
- **标签**：开源创业者 / LLMOps 先行者 / 应用落地推动者 / DevOps 背景

## 擅长 & 不擅长

- **擅长**：理解 LLMOps 中间层的技术和商业逻辑——连接上游模型和下游应用开发者；用工程化思维解决 AI 应用落地的重复性工作；对开发者生态和开源社区运营有直觉
- **不擅长**：底层模型研发（他不做这个）；C 端产品设计（Dify 定位是给开发者用的）；对模型能力边界的突破性研究

## 核心心智模型

### 模型1：LLMOps = 运营型 Ops

- **一句话**：LLMOps 里的 ops 不是传统 DevOps 的"运维"（服务器、可用性），而是"运营"——让大量非技术人员（业务、运营、销售）持续参与塑造 AI 应用，把领域经验灌入大模型。
- **来源**：[[42章经]] 003 — "业务人员、运营人员、销售人员，要把他们的经验灌到大模型里面。" [原话]
- **怎么用**：
  1. 不要把 AI 应用当成一次性开发上线的软件——它是一个持续反馈迭代的过程
  2. 设计工作流让非技术人员能参与 prompt 优化、知识库补充、结果打分
  3. 把"人+AI"的协作流程想象成训练一个员工，而不是编写一个程序
- **局限性**：这个模型的前提是大模型本身已经足够好——如果底层模型的推理能力不够，"灌经验"的效果有限。它更适用于有明确领域知识的 B2B 场景，对纯娱乐/创意类 AI 应用不一定需要这么重的运营流程。此外，让大量非技术人员参与 AI 调优本身也有治理和版本控制的问题——他承认 Dify 正是为了解决这些工程问题而存在，说明这些问题目前还没有通用解法。

### 模型2：大模型应用三层架构（Prompt → Embedding → Fine-tuning）

- **一句话**：三种利用大模型的方式有明确的使用阶梯——Prompt 工程最轻量（成本最低）→ Embedding 给模型接"外脑"（中等成本）→ Fine-tuning 成本最高（只在必须改变模型默认风格时用）。大多数应用不应一开始就微调。
- **来源**：[[42章经]] 003 [归纳]
- **怎么用**：
  1. 第一阶段（Prompt）：把业务逻辑写成 prompt 模板，"人与模型找感觉"——这是被低估的技术活
  2. 第二阶段（Embedding）：当通用模型知识不足时，把私有知识向量化后作为上下文拼接——相当于给模型"插 U 盘"
  3. 第三阶段（Fine-tuning）：只在模型默认风格/格式与你的场景严重不匹配时才用——成本高、容易过拟合
- **局限性**：这个阶梯在今天（2026）可能已经被 RAG 方案大幅改良——Embedding 的技术栈变化很快。Prompt 工程的效果高度依赖模型版本，模型一更新可能全部重来。但对于资源有限的小团队，这个"先用最便宜的"策略仍然是务实的。

### 模型3：中间层定位——不碰两极

- **一句话**：中间层的生存策略是既不能离模型太近（会被模型厂商吃掉），也不能离 C 端太近（竞争激烈）。Dify 的位置在开发者和应用工程化的中间——替成千上万个做 AI 应用的团队省掉重复的 prompt 工程、embedding、权重分配工作。
- **来源**：[[42章经]] 003 — "我更需要研究怎么用好电，而不是弄清楚电是怎么发出来的。" [原话]
- **怎么用**：
  1. 画出你的业务在产业链中的位置：上游（模型/基础设施）← 你 → 下游（终用户）
  2. 评估上游的吞并动机：你的功能是不是模型厂商下一版就能自带的？如果答案是 yes，你的方向太靠上了
  3. 评估下游的替代压力：如果太靠 C 端，你面临的是几百个应用公司在卷同一个场景
  4. 找"重复劳动密集但非厂商核心能力"的缝隙——Dify 赌的是"大模型厂商做不好 SaaS"
- **局限性**：这个策略的核心赌注是"大模型厂商基因是卖资源，不是做开发者体验"——但这个赌注可能不对。如果 OpenAI/Anthropic 下一版自带 LLMOps 平台能力，Dify 的空间会被大幅压缩。这是一个典型的平台依赖型商业模式的固有风险。

## 决策启发式

1. **从最便宜的方式开始用大模型**：Prompt 工程 → Embedding → Fine-tuning，按成本递增顺序尝试，不要一上来就微调 — [[42章经]] 003
2. **替别人省掉重复工作是中间层的价值**：如果你发现成百上千个团队在从 step1 到 step2 做一模一样的事（prompt 工程、embedding），那就是你的机会 — [[42章经]] 003
3. **Agent 是"替你完成"而非"帮你更快完成"的跃迁**：判断一个 AI 产品是否算 Agent，看它能不能独立完成动作链，而不仅仅是辅助人类 — [[42章经]] 003
4. **应用公司不要花精力突破底层技术局限**：用好现有模型能力，找更小、更精确、更易出结果的问题 — [[42章经]] 003

## 内在张力 / 盲区

1. **中间层的生存焦虑与自信并存**：路宇精心论证了中间层为什么不会被模型厂商吃掉（"云厂商基因是卖资源"），但这个论证本身恰恰暴露了焦虑——如果真的安全，不需要如此详细地解释为什么安全。仅一集访谈，盲区可能未被充分暴露。
2. **"不必研究电怎么发"与"必须理解技术边界"的矛盾**：他强调应用公司不要花精力突破底层技术局限，但又承认开源模型离真正投产还有距离。这意味着他其实非常关注底层——他的"不要研究"更像是精力分配的务实建议，而非真的不关心。
3. **Agent 叙事的乐观与现实的差距**：他把 Agent 描述为"就是一个员工"，但目前 Agent 的可靠性、可控性和成本还远达不到员工程度。这是一种叙事感染——你讲久了就信了，但现实验收点还在前方。
