# 044 - 从 E2B 到 Browserbase Agent Infra 新热点中有哪些大机会 对谈 Grasp 创始人雷磊

## 摘要

本期对谈围绕 Agent Infra 展开。Grasp 创始人雷磊认为，Agent 不是传统 SaaS 的换皮，而是一类新的“结果交付主体”。当软件从“给人使用”转向“给 Agent 使用”时，产品设计的核心会发生变化：人是单线程、局部推进、可承担责任的使用者；Agent 则是可并行探索、需要实时反馈、且必须被放入明确安全边界中的执行主体。

在这个框架下，E2B、ForeverVM、Browserbase 等产品代表了早期 Agent 环境公司的不同切入点：代码执行沙盒解决安全和快速启动问题，状态保持解决长任务与资源成本问题，云端浏览器解决 Agent 与 Web 世界交互的问题。雷磊进一步提出，未来最重要的不是把现有软件简单接入大模型，而是为 Agent 设计真实反馈循环，让 AI 通过环境与世界交互，从结果中学习，而非只依赖人类判断。

## 金句收藏

- Agent 和 SaaS 不是同一种东西：SaaS 是工具，Agent 交付的是结果。
- 给人设计软件和给 Agent 设计软件，应该从完全不同的出发点开始。
- 人类执行更像贪婪算法，Agent 可以在执行层面并行探索全局最优。
- 为 AI 设计系统，关键不是规定每一步流程，而是设计最后的反馈信号。
- 安全不是一个抽象标签，更重要的是把 Agent 的影响控制在可接受边界内。
- 未来 Agent 的环境至少应该云端化，客户端只是信任与展示层。
- Browser 和 coding 是 Agent 与世界交互的两个基础环境。
- AI 要真正创新，必须从真实世界的反馈中学习，而不是无限逼近人类专家的偏见。
- AI 环境是一个 AWS 级别的机会，但最后谁抓住它，并不由现有云厂商身份决定。

## 核心要点

### 1. Agent 不是 SaaS，而是新的服务对象

雷磊区分了 SaaS 与 Agent：SaaS 是给人使用的工具，Agent 则像一个可以交付结果的主体。未来既会有通用 Agent，也会有大量垂直小 Agent，数量可能远超今天 SaaS 的数量。它们类似更细分、更垂直的“店铺”，只要在特定领域能稳定交付结果，就可能形成可持续业务。

### 2. 人和 Agent 的两类关键差异

第一是工作方式不同。人类是单线程执行，即便事前有规划，落到行动上仍然是一件事一件事推进；Agent 可以并行尝试上百种路径，再把结果反馈给系统继续迭代。

第二是责任边界不同。人可以为自己的操作负责，但 AI 生成代码、操作网页、调用工具后造成的后果，需要通过沙盒、权限、状态隔离等方式被限制在可接受范围内。

### 3. Agent 产品设计的核心是反馈循环

传统软件强调流程设计：引导人一步一步完成任务。面向 Agent 的系统更重要的是设计反馈信号，让 Agent 知道某个行为对最终目标产生了正向还是负向影响。雷磊强调，反馈信号最好来自真实结果，而不是人类对中间行为的主观评价。

### 4. E2B 代表代码执行环境，ForeverVM 代表状态痛点

E2B 提供让 AI 运行代码的安全沙盒，并通过 microVM 等技术降低启动延迟。它的价值不只是“虚拟机”，而是把底层云资源包装成 Agent 可直接使用的运行环境。

ForeverVM 则强调状态保持：Agent 可能先执行一段脚本，隔一段时间再回来继续执行，如果每次都重启环境，既浪费资源，也破坏上下文。因此，能在低资源消耗下保存执行状态，是人类开发场景中不明显、但 Agent 场景中很重要的新需求。

### 5. Agent 环境会云端化

雷磊认为，Agent 的模型和执行环境天然适合放在云端。原因包括：需要弹性资源、长期运行、多线程并行、安全隔离，以及与云端模型低延迟协同。本地客户端仍会存在，但更多承担展示、确认与建立信任的作用。

### 6. Browserbase 与 Grasp：面向 Agent 的浏览器环境

Browserbase 的核心是把浏览器云化，并优化 AI 读取网页、获取上下文、执行自动化任务的能力。它早期服务的客户可以包括爬虫、自动化测试、RPA 等已经存在的机器流量场景。

Grasp 认为，仅做 runtime 层壁垒不够。一个面向 Agent 的浏览器可分为三层：底层 runtime，负责网页拉取、脚本执行、渲染；中间 agentic 层，负责理解页面、推理步骤、控制交互；上层 knowledge 层，是垂直行业 know-how。Grasp 选择把 runtime 和 agentic 两层合并封装，降低开发者构建浏览器 Agent 的工程难度。

### 7. 给 Agent 用的浏览器不同于给人用的浏览器

雷磊列出几个差异：

- 必须跑在云端，因为 Agent 不睡觉，且可能长时间并行执行。
- 可以 headless，不一定需要像人一样看见图形界面。
- 登录和凭证处理要重新设计，既要让 Agent 能完成登录，又不能把账号密码暴露给大模型。
- 需要 stateful browser，让 Agent 在长任务中断后恢复到原页面与状态，而不是重新开始。

### 8. Agent Infra 的更大机会

除 coding 与 browser 外，未来还会出现身份、电话、短信、支付、传感器、空间智能等面向 Agent 的工具与环境。雷磊认为，coding 环境解决逻辑执行，browser 环境解决与 Web 信息和行动的交互，这两类是最基础的 Agent 环境。

### 9. 真实反馈是 AI 创新的前提

雷磊用“川菜菜谱”举例：如果让大厨判断菜谱好坏，AI 最多逼近大厨的偏好；如果真的按菜谱做菜，再把好吃或难吃的结果反馈给 AI，它才有可能突破人类厨师的经验边界。Agent Infra 的重要性就在于，它让 AI 能进入真实环境并获得 grounded signal。

## 关键问答

### Q1：为什么说 Agent 与 SaaS 不同？

A：SaaS 是人使用的工具，价值在于提升人的效率；Agent 更像一个交付结果的主体。面向 Agent 设计产品时，不能只把现有 SaaS 加一个大模型入口，而要重新考虑工作方式、反馈机制和责任边界。

### Q2：Agent 与人的最大差异是什么？

A：一是执行方式。人类单线程推进，Agent 可以并行尝试多种路径。二是责任归属。人可以为行为负责，Agent 的行为必须被放在明确安全边界中，防止影响外溢。

### Q3：为什么 E2B 这样的沙盒会成为热点？

A：Agent 生成代码后需要运行，但不能无约束地在用户机器上执行。E2B 的价值在于提供安全、快速、可弹性的执行环境，把 AI 的影响限制在沙盒边界内，同时支持高频启动和并行执行。

### Q4：Browserbase 做的是什么？

A：Browserbase 提供给 AI 使用的云端浏览器运行环境，帮助 Agent 获取网页上下文、执行网页操作，并解决传统爬虫、自动化测试、RPA 等场景中的网页变化、信息读取和稳定性问题。

### Q5：Grasp 与 Browserbase 的区别是什么？

A：按雷磊的划分，Browserbase 更偏底层 runtime；Grasp 希望同时做 runtime 与 agentic 层，把网页理解、任务推理、状态管理、安全登录等能力封装给开发者，让他们专注垂直行业知识。

### Q6：为什么 Agent 环境需要云端化？

A：Agent 需要长期运行、并行执行、弹性扩缩和安全隔离。模型本身也在云端运行，将执行环境与模型放在一起，可以减少延迟并提升协同效率。本地主要承担展示和用户确认。

### Q7：Agent Infra 会不会被云厂商直接吃掉？

A：雷磊认为，底层算力类似水电，云厂商会提供基础资源；Agent Infra 更像装修与交付层，理解 Agent 的具体痛点并包装成可用环境。短期更应关注合作和市场增量，而不是过早假设零和竞争。

## 润色版逐字稿

### 开场：为什么聊 Agent Infra

主持人介绍，本期邀请 Grasp 创始人雷磊，讨论 Agent 热潮之后的新机会。此前市场集中关注通用 Agent、垂直 Agent 与 Agent 平台，但主持人认为，下一波更值得关注的可能是“给 Agent 用的产品”。Grasp 正在做的就是给 AI 使用的浏览器。

雷磊先澄清一个判断：很多 SaaS 公司会把自己包装成 Agent，但 Agent 与 SaaS 本质不同。SaaS 是工具，人需要去使用它；Agent 交付的是结果。因此，未来为 Agent 设计软件，不能沿用给人设计软件的思路。

### Agent 的数量与形态

雷磊认为，未来不会只有一种通用 Agent，也不会只有垂直 Agent，而是两者长期共存。大型通用 Agent 类似综合商超，垂直 Agent 则像无数细分店铺，只要能在某个垂直领域交付更好的结果，即使用户规模不大，也能形成生意。

在他看来，Agent 的数量会远超 SaaS，因为 SaaS 是通用工具，而 Agent 是结果交付主体。只要一个结果可以被稳定交付，就可能诞生一个对应的 Agent。

### 人和 Agent 的关系：不是对立，而是协作进化

主持人提出，未来是否会从“工具服务人”变成“人辅助 Agent”。雷磊认为，不必把人和 Agent 放在对立面。关键不是谁处在主体地位，而是谁能交付更好的结果。如果人辅助 AI 能产生更好的结果，这种模式就有价值。

他把当前 AI 发展放在更长阶段中看：从聊天、推理，到 Agent，再到创新。到了创新阶段，AI 可能产生人类没有想到的结果。只要这种结果对世界有正向作用，就不必执着于人类的地位叙事。

### 工作范式差异：从流程设计到反馈设计

雷磊用写代码举例。人类写代码时，通常先写第一个方法，再写第二个方法，然后把不同方法串联成工作流。AI 的方式可能完全不同：它可以同时生成一百个方法，运行后比较结果，再把反馈输入系统，继续生成下一步。

这意味着，面向 AI 的系统不应只关注流程编排，而要关注反馈循环。系统要能判断每一步执行对最终目标是正向还是负向，并把这个信号反馈给模型。

主持人把这种差异类比为“人类像贪婪算法，AI 更接近动态规划”。雷磊认可这个比喻：人执行时只能一步一步打开局部地图，AI 则可能在执行层面同时探索多个方向，从全局结果中寻找更优路径。

### AlphaProof 与真实反馈

雷磊提到 DeepMind 的 AlphaProof。它不是像人一样学习解题步骤，而是把数学问题转换成机器可识别的形式，并设计反馈信号，让系统自己推导和训练。这个例子说明，为人设计解析系统时，需要引导他一步一步完成；为 AI 设计系统时，关键是定义最后的反馈信号。

Grasp 设计浏览器时也采用这种思路：在每一步操作结果中设计奖励机制，判断执行对最终任务产生了正向还是负向影响，再把它反馈回系统。雷磊强调，最好的反馈应来自真实结果，而不是人类对中间行为的评价。

### 安全边界：为什么 Agent 需要沙盒

第二个关键差异是责任。人写代码并在自己电脑上运行，出了问题由人承担；AI 生成并执行代码时，如果删掉文件或破坏环境，责任归属就不清晰。因此，Agent 需要沙盒，把影响控制在明确范围内。

E2B 的价值就在这里。它提供安全沙盒，让 AI 运行代码，并通过 microVM 等技术实现很快的启动速度。快速启动不仅是体验问题，也服务于 Agent 的并行探索：越快获得结果，越能高效反馈和迭代。

### 云端环境与本地工具的边界

主持人问，Cursor 这类工具是否算本地化。雷磊认为，Cursor 更像 copilot，主要辅助人生成代码；当它越来越像 Agent，执行架构就会自然迁向云端。未来强大的 Agent 环境应在云端运行，本地客户端只负责展示和建立信任。

人类使用 AI 编程工具时，也在从“审查每行代码”转向“只关注执行结果”。这要求环境能够被信任，而云端隔离、可观察和状态控制会成为基础设施能力。

### E2B、云厂商与 Agent SaaS

主持人追问，E2B 与云厂商是什么关系。雷磊用房子类比：云厂商提供水电等基础资源，E2B 把这些资源包装成 Agent 可使用的环境。两者短期并非冲突关系，AI 市场还在增长阶段，更重要的是把蛋糕做大。

他认为，给 Agent 用的环境或工具可以看作“给 Agent 用的 SaaS”，但 Agent 本身不是 SaaS。Agent 是主体，Agent SaaS 是服务这个主体的软件。

### ForeverVM：状态保持是 Agent 新痛点

雷磊提到 E2B 的竞争对手 ForeverVM，它强调的不是安全，而是状态。人类写代码通常一次执行完一段脚本，状态消失也没关系；Agent 可能先执行脚本，再去做别的推理，一小时后回来继续执行。此时既要恢复上下文，又不能让环境一直热启动浪费资源。

这类痛点不是传统开发工具里最突出的，但在 Agent 并行与长任务场景下会变得重要。

### Browserbase：给 AI 用的浏览器

谈到 Browserbase，雷磊认为它是当前热门的 AI 浏览器基础设施公司。它把浏览器云化，并针对 AI 操作网页做优化，例如自动获取网站信息作为上下文，辅助 AI 操作页面。

Browserbase 很多客户可能来自传统爬虫、自动化测试和 RPA。它解决的是已有机器流量中“不够智能、网页变化后容易失效、上下文获取困难”等问题。

### 给 Agent 用的浏览器与人用浏览器的区别

雷磊总结了几类差异。首先，AI 浏览器一定跑在云端，因为 Agent 不睡觉，也可能长时间并行运行。其次，它可以 headless，不需要图形界面和鼠标操作。再次，登录和凭证处理需要特别设计：既要让 Agent 能自主完成登录，又不能把用户账号、密码和验证码暴露给大模型。

Grasp 为此设计了安全本地登录功能：当页面需要登录时，系统通过本地方式填入账号密码和邮件验证码，过程不把敏感信息传给大模型。

最后，AI 浏览器需要状态保持。例如 Agent 先在携程搜索机票，再把信息交给另一个系统推理，过一段时间回来继续购买。用户希望浏览器仍停留在之前页面，但云端不能一直占用资源。因此，stateful browser 是 Agent 浏览器的重要能力。

### Grasp 的产品分层

雷磊把 browser-use 能力分成三层。最底层是 runtime，负责网页访问、脚本执行和渲染。中间是 agentic 层，负责 AI 如何理解网页、获取信息、推理步骤并执行交互。最上层是 knowledge 层，即垂直行业 know-how。

他认为，真正构建垂直 Agent 的团队应主要关注最上层，而 Grasp 希望把 runtime 与 agentic 两层合并封装，提供通用工程能力。这样开发者可以像拼乐高一样使用底层环境，再加入自己的行业认知。

### 为什么 coding 和 browser 是两类基础环境

雷磊认为，coding 解决的是执行逻辑，browser 解决的是与 Web 信息和行动的交互。以 ChatGPT 的 deep research 为例，本质上也是模型加网页浏览能力，再加 Python 代码执行器。

除了这两类基础环境，未来还会有数学公式执行环境、物理传感器环境、具身智能环境、空间智能环境等。只要 Agent 需要与某类世界交互，就会需要相应环境。

### 当前 browser-use 像 2023 年的 AI coding

雷磊认为，今天的 browser-use 有点像 2023 年的 AI coding。大模型能否解决一个任务，取决于任务样本空间大小与模型成功率的乘积。代码任务在 GPT-3.5 后突破了可用阈值；网页操作样本空间更大，当前模型成功率还不够高，所以很多人觉得不实用。但随着模型能力提升，一旦达到阈值，browser-use 可能像 AI coding 一样快速普及。

### 真正的非共识：反馈循环

主持人问，为 Agent 做产品最重要的非共识是什么。雷磊回答，不同人会强调上下文、知识或模型，但他最看重反馈循环。环境的意义在于让 AI 与外部世界交互，获得真实结果，再通过奖励机制提升能力。

他认为，未来 AI 会从“学习人类数据”转向“自己体验世界”。只有真实反馈才能让 AI 突破人类认知边界，而不是无限逼近人类专家的偏见。

### 结尾：Agent Infra 的长期机会

雷磊认为，AI 环境是 AWS 级别的机会。未来云资源消耗和数据产生都会增加，云厂商有机会；但 AI native 的基础设施公司也可以从更贴近 Agent 使用场景的环境工具切入，逐步向下扩展。

对于何时真正爆发，他不做时间判断，但强调更重要的问题是：Agent 是否一定会来，以及当 Agent 到来时，我们能为它们提供什么价值。
