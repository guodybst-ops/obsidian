# Agent环境-工具-反馈设计框架

## 一句话

将Agent产品设计从强化学习视角理解：定义状态（context）、行动空间（工具调用）和奖励信号（反馈机制）。只有把产品变成一个可反馈、可收敛的环境，Agent才能持续迭代。

## 怎么用

### Step 1：定义状态（Context）

Agent当前看到和记住的一切：

- 用户目标：用户真正想要什么
- 环境状态：代码库结构、网页内容、数据表、API返回
- 历史步骤：前面做了什么、结果如何
- 用户偏好：过去的行为模式、偏好设置

关键操作：列出Agent需要感知的所有信息源，对每个源设计自动化获取方式。

### Step 2：定义行动空间（Tool/Action）

Agent能做什么：

- API调用（搜索、数据库、第三方服务）
- 代码生成与执行（AI Coding作为灵巧手）
- 浏览器操作（填表、点击、截图）
- 向用户提问（在不确定时获取澄清）

关键原则：优先复用已有可靠工具，工具不够用时才用AI Coding临时生成。每次从零生成代码会导致高成本、高随机性。

### Step 3：定义奖励信号（Feedback）

什么行为让结果更接近目标：

**好反馈信号的来源**（不应来自另一个prompt自我评价）：
- 代码运行结果（成功/失败/错误信息）
- 结构化字段校验（表格中是否有空值/缺失列）
- 真实数据库返回（SQL执行结果是否匹配预期）
- 用户操作结果（用户是否采纳/下载/继续使用）

**坏反馈信号**：
- 用另一个prompt让模型评价自己（容易循环）
- 只看最终结果不看中间过程（导致错误累积）

### Step 4：建立反馈闭环

1. Agent执行action → 环境返回新状态+奖励信号
2. 奖励信号判断这一步是接近还是远离目标
3. 如果远离→调整路径
4. 如果接近→继续前进
5. 形成"执行→反馈→调整→再执行"的闭环

### Step 5：判断环境是否足够好

检验标准：
- 能否基于行动结果提供清晰的奖励信号？
- IDE是好环境：代码生成后可直接运行，运行失败产生错误信息=天然反馈
- 浏览器不一定是好环境：需要额外搭建反馈系统
- 垂直场景更容易构建好环境：目标清晰、行动空间有限、结果可衡量

## 完整示例

以Sheet0的数据Agent推演：

```
场景：抓取YC公司列表，补全创始人信息和社交账号

Step 1 - 状态定义：
- 目标：获取YC W24批次所有公司+创始人+Twitter
- 环境：YC官网页面、LinkedIn、Twitter、Crunchbase
- 历史：已访问YC页面，找到公司列表URL

Step 2 - 行动空间：
- 工具1：网页抓取（MCP封装的浏览器API）
- 工具2：页面结构分析（LLM识别CSS选择器）
- 工具3：数据写入表格（结构化存储）
- 工具4：信息补全（通过其他API交叉验证）

Step 3 - 奖励信号：
- 正确信号：表格中每行都有公司名+创始人+Twitter（完整度100%）
- 错误信号：某行Twitter字段为空（缺失）
- 校验：通过Twitter API验证账号是否存在

Step 4 - 反馈闭环：
执行→抓取YC页面→识别公司列表→逐行补全信息→
检查表格完整度→发现3家公司缺Twitter→回退重新搜索→补全→完成

最终交付：一张完整的结构化表格
```

## 适用场景与边界

**适用场景**：
- 垂直Agent产品设计（有明确任务定义和可衡量结果）
- Agent创业公司在定义产品方向时
- 投资人判断Agent公司潜力时

**局限性**：
- 通用Agent很难应用：目标太泛、行动空间太大、奖励信号难以定义
- 有些任务没有清晰的ground truth（如情感陪伴）
- 仅1个来源 [AI推理]
- 构建好的环境需要大量工程投入
