# 从教师端 MVP 到可盈利产品路线图

> 当前状态：已经完成 Dify 老师端主控 LLM MVP。下一步不是继续堆 Prompt，而是把它变成学生能真实使用、老师/家长能看到结果、机构愿意付费的闭环产品。

## 1. 当前状态审计

### 已完成

- 已创建 Dify Chatflow：`PEP英语AI作业老师 MVP`
- 已能输入 PEP 单元内容并生成练习。
- 已加入主控 Prompt 中的对抗性审查逻辑。
- 已能输出 `student_view` 和 `teacher_key`。
- 已验证 Unit 1 样例能生成 JSON 题目。
- 已发布老师端 MVP。

### 当前不能直接商用的原因

- 当前版本会同时输出学生题目和教师答案 key，不能直接发给学生。
- 当前没有学生端答题页面或安全答题流程。
- 当前没有题目、答案、学生作答、错题、再练结果的稳定数据记录。
- 当前学习报告还不是基于真实学生历史数据生成。
- 当前没有用户验证、收费验证和机构使用场景验证。

## 2. 终局倒推：像师者AI一样可投入使用，至少需要什么

一个可用、可收费的 AI 教育产品，至少要满足 6 个条件：

1. 学生能独立使用：看题、作答、提交、拿反馈。
2. 答案不能泄露：学生端不能看到 answer key。
3. 老师能管理任务：生成作业、查看结果、看错题。
4. 家长/机构能看到价值：学习报告、薄弱点、再练结果。
5. 产品能稳定交付：出题不过度超纲，批改不乱判，异常可人工复核。
6. 有收费场景：老师省时间、机构能续费、家长觉得有效。

当前老师端 MVP 只满足了第 3 点的一小部分，所以下一步必须补第 1、2、4 点。

## 3. 下一步唯一优先级：学生端安全闭环 V1

### 为什么是它

如果没有学生端安全闭环，产品就只能是老师内部工具，不能形成真实使用数据，也无法证明“孩子有没有变强”。

下一步目标不是做漂亮 App，而是做到：

```text
老师生成作业
-> 系统隐藏答案
-> 学生只看到题目并提交答案
-> 系统批改
-> 系统生成错题再练
-> 老师/家长看到学习报告
```

## 4. 学生端安全闭环 V1 的验收标准

- [ ] 学生端只显示题目，不显示答案 key。
- [ ] 每套练习有唯一 `assignment_id`。
- [ ] 系统能根据 `assignment_id` 找到内部答案 key。
- [ ] 学生能提交答案。
- [ ] 系统能输出对错、错因、薄弱知识点。
- [ ] 系统能为错题生成 3 道同类再练题。
- [ ] 系统能生成一页老师/家长报告。
- [ ] 至少用 1 个真实学生完整跑通一次。

## 5. 技术路径选择

### 路径 A：继续用 Dify 拆多节点

适合：最快把当前 MVP 升级成真正工作流。

结构：

```text
Start
-> Question Classifier
-> 生成题目 LLM
-> Code 节点拆分 student_view / teacher_key
-> 保存 teacher_key 到会话变量
-> Answer 只输出 student_view
-> 学生提交答案
-> 批改 LLM 使用内部 teacher_key
-> 审批改 LLM
-> 再练 LLM
-> 报告 LLM
```

优点：沿用当前 Dify，速度快。

风险：Dify 会话变量、跨用户作业、答案 key 隔离能力需要实测；如果处理不好，仍可能泄露答案。

### 路径 B：Dify + 表格/数据库

适合：最稳的无代码/低代码 MVP。

结构：

```text
老师端 Dify 生成 assignment_package
-> 写入飞书表格/Airtable/Supabase
-> 学生用表单提交答案
-> Dify 读取答案 key 和学生答案批改
-> 报告写回表格
```

优点：答案 key 可以和学生端分离，数据沉淀清晰。

风险：交互不像完整 App，但足够验证真实需求。

### 路径 C：做极简 Web App

适合：验证后进入产品化。

结构：

```text
前端：学生做题页 / 老师生成页 / 报告页
后端：assignment、answer、grading、retry、report API
数据库：Supabase / Postgres
AI：Dify API 或 OpenAI/New API
```

优点：最接近可收费产品。

风险：开发量变大，没验证前不建议先做。

## 6. 推荐路线

当前推荐：先走路径 B，必要时结合路径 A。

原因：

- 当前最重要的是验证学生真实使用和老师/家长是否认可，不是做完整 App。
- 表格/数据库能先解决答案 key 隔离和数据记录问题。
- Dify 继续负责 AI 出题、审查、批改、再练、报告。
- 后续如果验证有效，再把表格替换成真正数据库和学生端页面。

## 7. 未来 4 个版本

### V0.1 老师端 MVP（已完成）

- 老师输入单元内容。
- Dify 生成题目和答案。
- 适合老师内部使用。

### V0.2 学生端安全闭环（下一步）

- 答案 key 隐藏。
- 学生可提交答案。
- 系统可批改、生成再练和报告。
- 目标：跑通 1 个真实学生。

### V0.3 小班试点版

- 支持 5-10 个学生。
- 有作业记录表。
- 有每个学生的正确率、错因、再练结果。
- 目标：找 1 位老师或 1 个小机构试用。

### V0.4 付费试点版

- 有体验包和报价。
- 有老师/家长报告模板。
- 有机构试点话术。
- 目标：拿到第一个付费或明确付费意愿。

## 9. 先不要做的事

- 不要先做完整小程序。
- 不要先扩全年级/全学科。
- 不要先做复杂账号系统。

- 不要把当前老师端 Dify 链接直接发给学生。

## 10. 下一步具体执行建议

下一步应该做：

> 搭建 V0.2 学生端安全闭环：用 Dify 生成题目和报告，用表格/数据库存储 answer key 和学生提交记录。

最小实现方式：

1. 用 Dify 老师端生成 `student_view` 和 `teacher_key`。
2. 把 `student_view` 发给学生，`teacher_key` 存进表格。
3. 学生用表单提交答案。
4. 老师把学生答案和 `teacher_key` 交给 Dify 批改。
5. Dify 输出错因、再练题和学习报告。

这个版本虽然还不是完整产品，但它能产生最关键的证据：学生是否能用、老师是否省时间、家长是否认可、是否值得继续产品化。
