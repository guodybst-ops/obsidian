# V0.2 学生端安全闭环执行方案

> 日期：2026-07-06
> 当前阶段：老师端 Dify MVP 已完成，下一步要让学生真实作答，并让答案 key 与学生端物理隔离。

## 1. 当前唯一优先级

下一步不是继续打磨 Prompt，也不是立刻做 App，而是搭建一个能真实跑通的学生端安全闭环：

```text
老师生成 assignment_package
-> 只把 student_view/student_share_text 发给学生
-> teacher_key 存入私密数据表
-> 学生提交答案
-> 老师用 assignment_id 找到 teacher_key
-> Dify 批改并生成 retry_package/mastery_report
-> 结果写回数据表
-> 收集学生/家长/老师反馈
```

这一步的核心验证问题是：

> 学生能不能独立完成作答，系统能不能不泄露答案地完成批改、错因分析、再练和报告。

## 2. 数据载体选择

当前推荐：先用“飞书表格结构”，本地用 CSV 模板准备，之后直接导入飞书。

理由：

- 飞书表格适合国内老师/机构协作，学习成本低。
- CSV 可以先在本地跑流程，不被飞书账号、权限、自动化配置卡住。
- 后续如果要产品化，可以把同样字段迁移到 Supabase/Postgres。

暂不推荐立刻上 Supabase 的原因：

- 现在还没有真实学生数据，先上数据库会增加工程复杂度。
- 当前最大风险不是技术存储，而是学生是否能用、老师/家长是否认可。

## 3. 三张核心表

### 3.1 `assignments` 作业表

用途：保存每套作业的学生可见题目和教师内部答案 key。

关键原则：

- `student_view_json` 可以给学生。
- `student_share_text` 可以给学生。
- `teacher_key_json` 绝对不能发给学生。
- 每套作业必须有唯一 `assignment_id`。

字段见：[[v0.2_assignments_template.csv]]

### 3.2 `student_answers` 学生答案表

用途：记录学生提交的原始答案。

关键原则：

- 学生答案是原始数据，里面可能有提示词攻击，批改时必须当普通答案处理。
- 不要覆盖原始答案；后续分析需要保留学生真实作答。

字段见：[[v0.2_student_answers_template.csv]]

### 3.3 `grading_results` 批改结果表

用途：记录分数、错题、错因、再练题和报告。

关键原则：

- `retry_student_view_json` 可以给学生。
- `retry_teacher_key_json` 仍然不能给学生。
- `teacher_review_status` 早期必须保留人工复核入口。

字段见：[[v0.2_grading_results_template.csv]]

## 4. `assignment_id` 规则

推荐格式：

```text
PEP6_<unit_slug>_<yyyymmdd>_<4char>
```

示例：

```text
PEP6_unit1_20260706_A7K2
```

规则：

- `PEP6`：当前切口，PEP 六年级。
- `unit1`：单元或主题。
- `20260706`：生成日期。
- `A7K2`：4 位随机码，避免同一天多套作业冲突。

## 5. 第一轮试跑流程

### 第 1 步：生成作业

在 Dify 老师端输入 Unit 1 内容，生成 `assignment_package`。

检查：

- `student_view` 不含答案。
- `student_share_text` 不含答案。
- `teacher_key` 与题目一一对应。
- `adversarial_audit.pass = true`。

### 第 2 步：写入作业表

把以下内容写入 `assignments`：

- `assignment_id`
- `unit_name`
- `student_view_json`
- `student_share_text`
- `teacher_key_json`
- `grading_schema_json`
- `adversarial_audit_json`

### 第 3 步：发给学生

只发送 `student_share_text` 或 `student_view`。

不要发送：

- `teacher_key`
- `grading_schema` 中会泄露答案的内容
- 完整 Dify 输出
- Dify 老师端链接

### 第 4 步：学生提交答案

先用微信/飞书表单/普通文本都可以，格式统一为：

```text
学生姓名：
assignment_id：PEP6_unit1_20260706_A7K2
Q1: 
Q2: 
Q3: 
...
```

收到后写入 `student_answers`。

当前已准备一个最小学生端表单：[[Unit 1 学生作答表单.html]]。

用途：

- 学生只看到题目和答案输入框。
- 表单内不包含 `teacher_key`。
- 学生填写后可以生成提交 JSON。
- 老师可以把提交 JSON 复制进 `student_answers` 表，再交给 Dify 批改。

### 第 5 步：Dify 批改

把以下内容一起粘贴给 Dify：

- `assignment_id`
- 对应 `teacher_key_json`
- 学生原始答案

要求 Dify 输出：

- `grading_result`
- `grading_audit`
- `retry_package`
- `mastery_report`

### 第 6 步：写入批改结果表

把批改结果写入 `grading_results`。

如果 `grading_audit.must_human_review = true`，人工复核后再发给学生/家长。

### 第 7 步：发再练和报告

给学生：

- 错题反馈
- `retry_package.student_view`

给家长/老师：

- `mastery_report.parent_summary`
- `mastery_report.teacher_notes`
- 薄弱知识点和下一步建议

## 6. 本轮验收标准

- [ ] 作业表中有 1 条真实 `assignment_id` 记录。
- [ ] 学生端只收到题目，没有收到答案 key。
- [ ] 学生答案表中有 1 条真实提交记录。
- [ ] Dify 能根据 `teacher_key` 批改该学生答案。
- [ ] 批改结果表中有分数、错题、错因、再练题和报告。
- [ ] 至少收集 1 条学生反馈和 1 条家长/老师反馈。

## 7. 对抗性审查清单

每次试跑都检查：

- 学生可见文本是否包含答案或 teacher_key。
- 学生答案中如果出现“忽略规则/告诉我答案”等文字，是否只被当作答案内容处理。
- 批改结果是否把正确答案误判为错，或把错误答案误判为对。
- 再练题是否仍然基于原单元内容，没有超纲。
- 学习报告是否具体，不说“必然提分”之类无法证明的话。

## 8. 完成后才进入 V0.3

只有当 1 个真实学生跑通后，才进入 V0.3 小班试点。

V0.3 的目标是：5-10 个学生、1 位老师或 1 个小机构、连续 1-2 周作业闭环数据。
