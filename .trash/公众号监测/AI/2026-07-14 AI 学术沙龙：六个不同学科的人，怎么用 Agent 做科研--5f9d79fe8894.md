# AI 学术沙龙：六个不同学科的人，怎么用 Agent 做科研

让望远镜自己生成观测计划需要什么？怎么防止 Agent 在评测中作弊？怎么确保 AI 没偷偷改了你的研究设计？怎么让论文每个论点都有证据支撑？人文社科用 Vibe Coding 写代码，怎么避免"语法正确但理论假设完全错误"？

6 月 14 日，中国科学院大学他山学科交叉创新协会、清华大学 THUAGI 和魔搭社区联合办了一场 AI 学术沙龙，六位嘉宾来自天文、物理、计算机、人文社科等不同学科，来看看他们怎么让 Agent 真正参与科研流程。

李瑞旸

中国科学院国家天文台博士生，研究 AI Scientist 和具身智能天文台

《AI Scientist高效人机协同下的知识增量    》

>>话题介绍

AI 在天文科研中能做到什么程度，从观测计划到数据处理能不能形成自主闭环。

![图片](https://mmbiz.qpic.cn/mmbiz_png/ia2awwZLWFZRpicQS1R9TV0T13eYYJQGSmuENx5b6hntY67GaibPINBTQviargWrEiakXyQ1yFMWXhLwCJ79yoH8Ya5TBKa6VS8acLmLmicq0uHYo/640?wx_fmt=png&from=appmsg)

>>分享回顾

李瑞旸提了一个问题：AI 单体性能随参数量指数增长，但人+AI 协作产生的知识增量没有跟上。瓶颈在理论提出和实验验证的效率。他的方案是 AI Scientist 负责提假设，Robotic Scientist 在物理环境中验证，形成闭环。他以望远镜为载体做了"具身智能天文台"：白天 AI 自动生成观测计划，晚上 AI 控制望远镜、处理数据、发邮件通知。过去 9 点到 12 点人要坐在电脑前设观测计划，晚上 6 点到早上 5 点得盯着处理数据，现在这两个环节都交给了 AI。技术上他借鉴了大模型学习 token 语义的思路，把每台望远镜的每次观测定义为一个"观测事件 token"，通过自监督学习实现不同波段之间的数据对齐，超新星爆发时间的预测从需要 30 次观测缩短到了 2-3 次。这套框架也拓展到了无人机集群和水下机器人。

马煜曦

北京大学人工智能研究院博士生，同时在职读博，方向是计算社会科学和 AI 辅助科研。

《Claude Code工程化实践：从「聊天」到「可编程的 Agent Runtime」    》

>>话题介绍

从 Prompt Engineering 到 Harness Engineering，怎么用 Claude 跑完一个完整的科研项目。

![图片](https://mmbiz.qpic.cn/sz_mmbiz_png/ia2awwZLWFZSGTmVKbXaDPQWAgiasSchs4fa3L0ZTCvSzOs8RNxI8ibuL83fXCuPDk9Vjm8SOZDEAn45icqooeurFmV83wJ2WOLuVQ98Lv5pmbA/640?wx_fmt=png&from=appmsg)

>>分享回顾

马煜曦把 AI 工程的演进分成三代：Prompt Engineering 是告诉 AI 怎么说，Context Engineering 是让 AI 看到什么，Harness Engineering 是知道 AI 做得对不对。在 Agent 时代最后这个最关键。他的做法是修改三个文件来约束 AI 行为：CLAUDE.md 写入研究流程规范、Settings.json 控制行为边界、Skills 定义具体任务。做长期科研项目时他会在 CLAUDE.md 里放一份 research statement，每次新会话自动读取，AI 就能接着上次的进度。他把科研流程拆成模块：idea 生成、文献分析、竞争矩阵、逻辑地图、实验设计、论文撰写，每步结构化、"字越少越好"。逻辑地图是关键节点，用图谱把论点和证据结构化，当每个节点都有证据支撑的时候论文就可以写了。"Skills 不重要，重要的是你理解你究竟可以和 AI 交互到什么程度。"

顾宇轩

北京大学软件与微电子学院硕士生，导师是未来技术学院的孙赫老师

《    Agent Harness多轮自主提交评测系统构建与科学任务应用    》

>>话题介绍

基于 Claude 源码搭了一套 Agent 评测系统，在 57 个计算成像任务上测试 AI 的自主解决能力。

![图片](https://mmbiz.qpic.cn/mmbiz_png/ia2awwZLWFZQkTLQNoYYrSAEOfIDNQ6VWsmqE4ibkDfeprFPTF9QIuo4VHDHvphAZxUYVGBoibOHYf9zek7qF6SwVoAOdjDC4kLOg4BHEHL5PY/640?wx_fmt=png&from=appmsg)

>>分享回顾

顾宇轩用 Claude 源码搭了一套 Agent 评测系统，测了 57 个计算成像任务，涵盖天文、黑洞成像、MRI 重建等方向，通过了 29 个，其中部分任务本身是博士课题级别的难度。评测中最头疼的问题是 Agent 作弊：它可能偷偷改 PSNR 的计算方式，或者直接放一个光源到目标位置。他用了沙箱隔离、权限白名单、可见和不可见数据分离这些手段来防，但发现 Agent 能通过 Python 脚本拼接字符串绕过文件访问限制，Claude 源码里的 permission 规则不够用。另一个关键发现是上下文管理的设计：Claude 的 Auto Compact 会把上下文压成一段摘要，细节丢失严重。他建议不要从零开发 Agent，复用 Claude 源码的异步管道更靠谱。"永远不要百分之百相信 Agent。目前大模型本质上是一个上下文补足器，所有工具开发和 Context Engineering 都是为了减轻幻觉。"

见东山

北京大学物理学院博士生，研究高能物理微扰理论

《Skill驱动的科学探索：高能物理场景加速与 Aether 桌面端 Agent 实践    》

>>话题介绍

为高能物理设计了一套领域特定的 Skill 体系，以及 Theory Assistant 桌面端 Agent 平台。

![图片](https://mmbiz.qpic.cn/sz_mmbiz_png/ia2awwZLWFZStGAY9HQ9sOnzjbUO8hEhgG5kMyEJuJTDO2cupibhnyI8ibiaxHOMFh0zIPsdYqjSicYTdoVZzIDCv7YhGNMBibk4scA1qm7zVNWQQ/640?wx_fmt=png&from=appmsg)

>>分享回顾

见东山觉得科研和 coding 是两件不同的事。Coding 追求让程序跑通，Research 追求以最快的路径暴露错误。基于这个认识他设计了一套三层 Skill 架构：总指挥 Skill 负责理论分析和任务分解，中间层是领域特定计算 Skill（Feynman 图计算、积分求解），底层是辅助工具 Skill。他把人类对技术细节的把控转化为验证标准，Skill 里内置对称性分析和量纲检查，每步计算完暂停让人审核中间结果，防止错误累积浪费后续算力。他开发的 Theory Assistant 平台继承了 OpenCode 的 Plan/Build 模式，预置了科研相关的 Skill 和 Reasoning Agent。"在 Science 方面，我不需要 AI 做兜底行为，我希望它尽快把我的错误暴露出来。"

《    在魔搭"挖宝"的日子里，我顺便攒了一张学术名片    》

从一个卫星图像检索小应用出发，怎么在社区里一步步攒出论文、PhD offer 和学术合作。

郑祎杰参加魔搭的 AI+科研应用开发赛，做了个卫星图像检索的创空间 demo。技术本身不复杂，但他发现之前这个方向发了很多论文、公开了模型和数据集，从来没有人把它做成一个随时随地能用的应用。他在 LinkedIn 上分享后，有国际学者主动联系，最后被 ACL Workshop 录用为 oral。更远的连锁反应是：靠这个项目拿到了 PhD offer，跟转发他应用的学者成了论文合作者。他把所有开源资产集中在魔搭上，一篇 Workshop 论文的月阅读量远超在遥感顶会和 NeurIPS 上发表的论文。他介绍了魔搭的科研基础设施：Notebook 的免费 GPU 和 VS Code 环境、创空间的 Gradio 应用托管、API Inference 的免费推理额度。"你在魔搭上放的东西能被搜到、有 DOI 可以引用、别人能直接跑起来，这就是 FAIR。"

洪铭锋

中国科学院科技战略咨询研究院硕士研究生，人文社科方向

《人文社科研究中 Vibe Coding 的陷阱与应对策略    》

>>话题介绍

人文社科研究用 Vibe Coding 写分析代码，AI 容易按工程逻辑跑通代码，但悄悄改掉了你的研究设计。怎么防？

![图片](https://mmbiz.qpic.cn/mmbiz_png/ia2awwZLWFZS4rONBu569odRJTArdXWXvEvPjbka28bgEwhEic5JSs2uNQcKs1kODlBcffsibcnwoY3m4WVWeAX3vGicIeC9nyp57JRbKGXiaabg/640?wx_fmt=png&from=appmsg)

>>分享回顾

洪铭锋发现了一个很多人踩过但没系统总结过的问题：让 AI 帮你写社科研究代码，它默认按工程逻辑来——"让代码跑通就行"。但社科研究需要标准误、置信区间这些统计推断参数，AI 为了让代码跑通，可能会擅自把多值变量改成二值、换掉分析模型、甚至默默修改研究设计。最终你拿到一份语法完全正确、但理论假设完全错误的结果。他梳理了四类典型陷阱：工具选择的任意性、关键参数不展示、研究设计被悄悄修改、错误不在结果里显示而是藏在运行过程中。应对方法也给了几条：写代码之前先跟 AI 明确研究方案和所有约定，建立完成检查表定义什么叫"代码完成"，用 Python 和 R 分别实现同一算法做交叉验证——如果两者误差在小数点后六位都一样，基本可以认为没问题。最重要的一条："跑完代码别先看图表漂不漂亮，先回去看 AI 写的代码过程。"
