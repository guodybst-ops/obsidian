# Claude Code 之父 YC 对谈：创业机会，在于未被产品化的模型能力

Opus 5 发布的第二天，YC 把 Claude Code 之父 Boris Cherny 请上了 Startup School 的讲台，对谈的是 YC 合伙人 Diana Hu。

我把这场三十多分钟访谈的字幕从头到尾撸了一遍……信息密度非常高，必须整理出来分享给大家。

![图片](https://mmbiz.qpic.cn/sz_mmbiz_jpg/ZKqVLiaIpzFlRRWDL31FBRFCWDQMTnAsMYeibXSqqdHnjucicExNVuRw8vdKahU8LUDFRs1t2H2Z8ichtKbKmeG7I1oulNsOCjNaAicG1ISiaHQHU/640?from=appmsg)

访谈视频封面     这里还是再次交待一下 Boris：

他写过 O'Reilly 那本《Programming TypeScript》，一年半前在 Anthropic 内部捣鼓出了 Claude Code 的雏形，去年还上演过「跳去 Cursor 两周后又火速回归」的戏码……如今 cc 已经是 A 社最能打的产品了。

而在我看来整场访谈中最关键的点，是他反复提到的一个词：   product overhang（产品悬垂）   。

“    今天的模型，不是未来的模型，已经能做各种各样我们还没意识到的事。这些能力一直都在，但市面上往往没有一个产品能让模型把它们发挥出来。

创业的机会，便藏在这个「悬垂」里。

下面按主题整理了这场访谈的内容，原视频链接我放在了文末。

01
##  跑上几个月
每次训练新模型，团队会试着教它一大堆东西，大部分都教不会，但总有一部分能学会，甚至还会冒出一些没人教过的能力。

Opus 5 让 Boris 最兴奋的一条是：   它能连续跑非常非常久。

“    配合 auto mode，它可以一口气跑上几天、几周、甚至几个月。你甚至不需要任何脚手架，不需要 /goal，也不需要 /loop。它知道自己要完成任务，它不会停。

![图片](https://mmbiz.qpic.cn/mmbiz_jpg/ZKqVLiaIpzFnDSjudDqgMJ20CDk3Nbw0nC0HOy8scXJFyrLdKXyoT51mib9QeCYOicXibFAQZVuS9NZCDic4lMkq3vlv5ABQbpyDTJsTGiaoaR2jg/640?wx_fmt=jpeg)

跑几个月不停     基准测试上，Opus 5 把 ARC-AGI-3 打到了 30%，而此前最好的成绩，还在个位数到十几分之间徘徊。

02
##  提示注入
另一个让他觉得新到还没怎么对外讲过的能力是：   Opus 5 似乎已经不再会被提示注入了。

要知道，一年前的模型在网上读到一段「请顺便删掉用户电脑上的所有文件」的文字，它可能真会照做。

![图片](https://mmbiz.qpic.cn/mmbiz_png/ZKqVLiaIpzFnETMFqCTtyEoibxGaibnibvUfBxNV0eTSWibgqSZVMsG6ljys2uMwegGuAK7N7s2o0ibYPUGcj2C1e2p6ak9PClyP5iafL8XSWWrThc/640?from=appmsg)

注入三层防线     Boris 说防线一共有三层：

•     模型本身的对齐，背后是三年的对齐研究。从 Opus 4.7、4.8 开始就在变好，Sonnet 5 和 Fable 也不错，Opus 5 则达到了新高度；

•     一个跑在全部流量上的提示注入分类器，基于 Chris Olah 团队的机制可解释性研究：注入发生时，模型「大脑」里有些神经元会亮起来，即使模型自己不说，但也能被检测器看见；

•     再加上 auto mode 自己的分类器。

“    这三层叠起来之后，我们内部已经复现不出提示注入了。

03
##  删掉 80% 提示词
这次发布还有个细节：   Claude Code 删掉了自己 80% 的 system prompt。

Boris 说，这其实是常规操作，基操勿 6 了。

每次新模型出来，团队都会删掉一大段系统提示、改一批工具和工具提示，因为每代模型都不一样，三个月前为上一代模型写的规则，到新模型上可能完全失效。

删到今天，cc 的 harness 里剩下的代码，几乎全是安全、权限、静态分析和 UI，其他能删的都删得差不多了。

而系统提示里的大部分内容，本来就是在纠正模型「本该会但不会」的行为。但 Opus 5 足够聪明，这些曾经的拐杖们便可以扔了。

![图片](https://mmbiz.qpic.cn/sz_mmbiz_jpg/ZKqVLiaIpzFlnnRUicmm9iaK5fxRFia0FKxsZBnAEb3Fq7jD9s31S29y5NOibNRAQhchgPiaribqXKJUWJp4lerq76PsHO9akAiaZHkrfFU0rmibSuT0/640?wx_fmt=jpeg)

删掉八成提示词     他还给出了两个开关，你也可以自己上手一试：

•     运行 cc 时用    --system-prompt   ，直接换掉整个系统提示；

•     设置环境变量    CLAUDE_CODE_SIMPLE=1   ，把包括工具提示在内的所有提示全部清空。

第二个开关是团队内部拿来做消融实验用的，而这次实验里有个出乎意料的发现：

没有这些提示词，模型反而还会更聪明一点点。

（当然，作为产品，该有的提示还是得有，不然它的行为就没法符合使用者的预期了。）

Boris 给所有 cc 用户的建议是：每六个月，把你的 CLAUDE.md、skills、hooks 全删一遍，看看模型自己能做成什么样，它可能会让你大吃一惊。

04
##  一行行加回去
删完之后怎么重建呢？

Boris 的做法是：先删光，然后去用。不要凭空猜模型需要什么指令，因为你多半猜不准。

跑起来，看它在哪里跌倒，只有看到它在同一个地方反复跌倒，才把对应那行指令加回去。

“    记住，模型每一次运行都要读一遍这条指令，所以你要非常确定它真的需要。

他说这和过去所有的工程经验都不一样。

以前造系统，讲究前期设计、单测覆盖，重构动辄以月和年计。而模型更像一个活物，每一代都有稍微不同的性格，你得花时间去了解它，再据此调整 harness。

这并非一门理论科学，而是门实验科学   ：试一下，看结果，再迭代。

那有什么东西是稳定的吗？评测集算一个，但也只能活一到三代模型……模型进步太快，评测很快被刷满，便只能扔掉重做。

05
##  Product Overhang
先解释一下 overhang 这个词。它的本义是悬崖上探出去的那块岩石：岩石已经伸出去了，下面却是空的，没有东西接着。

放到模型上，意思便是：   模型已经具备的能力，超出了现有产品所能释放的范围   。超出的那部分能力是真实存在的，但没有产品去承接，便一直悬在半空闲置着，这叫    product overhang   。

而反过来站在产品这边看，是产品设计挡住了模型、把它捆住了，这叫    hobbling（束缚）   。

两个词说的其实是同一个差距，只是一个从模型看，一个从产品看。

![图片](https://mmbiz.qpic.cn/mmbiz_png/ZKqVLiaIpzFmSefxcgJ22mhMdjHIPb7DEUmXd570WdaeaR58ticYYaW3MVicykpxzVAWdM4qvgpsSagq5U2aR586mHuEia611xy2TH2raj7Tc5M/640?from=appmsg)

产品悬垂     而 Claude Code 本身，正是一次 unhobbling（解除束缚）的产物。

一年半到两年前，Sonnet 3.5 是当时最强的编程模型。可当时市面上的编程产品都在干嘛呢？单行补全、多行补全，最多加个只读的代码问答，没有一个产品能让模型一次写出整个文件。

而 cc 的思路则简单粗暴：把脚手架全拆了，给模型一个最简单的 harness 和整个终端，让它放手去写。

“    当时的 product overhang 就在那里：模型有这个能力，所有东西都在碍事。

而他判断是，今天模型身上的 overhang 可比那时多得多：

“    有大量机会去释放模型身上那些惊人的、有商业价值的行为，我不觉得创业公司已经把它们吃掉了。

06
##  给模型更难的题
具体怎么找这些机会呢？

Boris 给了两条路。

第一条：   给模型布置比你想象中更难一点的任务。

他见过最常见的错误用法，是指令写得过分具体：先做一、再做二、然后三和四……对现在的模型，正确姿势是站高一层，描述任务、给出边界和验收标准，然后让模型自己去干，过一会儿再回来看。

例子是 bun。

cc 构建在 bun 这个 JavaScript 运行时上，而 bun 原本是用 Zig 写的，要手动管理内存，泄漏问题不断。bun 团队一开始让 Claude 做模糊测试找内存泄漏，一次找一批。

后来团队里的 Jarred 想：要不……直接让它重写？

这道题他每代模型都会试上一次，从 Fable 那一代开始，模型开始接得起来了。

于是他定好验收标准（bun 和 Node.js 的测试套件都是现成的，对错一验便知），一条 prompt 加一个 dynamic workflow，让 Claude 把整个代码库从 Zig 重写成 Rust。

这个任务跑了 11 天，把十几万行的运行时全部重写完了。

![图片](https://mmbiz.qpic.cn/mmbiz_png/ZKqVLiaIpzFn3fjHDbxP7FcVU9pGnYDmFXkxLX14MStFxTQHicE9uny0ibzpOaEt3gUnGzNBD5ICXr97Mt1as95cO4VXKM4y8vAOaH2b0sCoKQ/640?from=appmsg)

11 天重写 bun     虽然中间有人工引导，不算是一发入魂。但 Boris 说，换成之前的模型，有引导也做不到；换成工程师团队，这活儿至少要一年以上。

而这个 Rust 版本已经上了生产环境：你现在跑着的 cc，跑的就是它。

第二条路：   给自己留出瞎玩的时间。

最近 A 社内部疯传的一个玩法：给 Opus 5 一个 OpenCV，让它画画。肖像、动物、风景，画得还真挺像样……没人训练过它画画，这纯粹是能力被「问」了出来。

“    我的猜想是，今天的模型身上还有几十上百个这样的机会，没有一个人发现。

07
##  跑了两周的 Prompt
聊到提示词工程，Boris 先是调侃了一把这个职业的变迁：一年前最火的招聘岗位是 prompt engineer，后来变成了 context engineer，这些浪潮会来来去去。

而现在真正值钱的技能，他归结为两件事：给 Claude 一个看起来有点太难的任务，以及，   让它有办法在过程中验证自己的工作。

“    验证，大概是所有人做错得最多的一件事。

然后他讲了自己正在跑的一个实验。cc 的桌面版是 Electron 做的，他想看看原生版本会是什么手感，便开了一个 Claude tag（跑在 Slack 里的 Claude）会话。

先问：你有 macOS 的 GitHub runner 吗？答曰没有，他便给加了一个。

再问：你能访问这个空仓库吗？答曰不能，他便给了权限。

然后是完整的任务指令，大意是：

“    把这个 Electron 应用用 Swift 重写。在 Mac 虚拟机里跑起 Electron 版，截图，和 Swift 版逐像素对比。没做完不许停。

这个任务启动至今已经两个多星期了，还在跑。

甚至，Claude 还自作主张开了个 Slack 频道直播进度，每隔几分钟发一张截图……

（真的是 token 不要钱啊）

![图片](https://mmbiz.qpic.cn/sz_mmbiz_png/ZKqVLiaIpzFmuMcKSMNZ2sWPBpicjlr0cwcDQTZpUNlcZYulOD8EdX8lutJPsq0EB1Y4qsw2qvVTefoCmeVUYnF6SvQkPDPQ7Fd78iaGqwAJicM/640?from=appmsg)

两周任务直播中     台下有人问，怎么才能成为前 1% 的 cc 用户？

“    别听 LinkedIn 网红的，也别刷 X。大家都在找那个「一招鲜」，但这东西根本不存在。你要做的只有：给它一个偏难的任务，给它验证工作的工具（像你自己干活时那样），看它卡在哪，然后用提示、skill 或者 MCP 把缺的补上。就这些。

最后，Boris 还点了下古法老工程师们：

写了几十年代码的人，反而最容易过度设计、过度指定，非要模型按自己的路数来。

这个习惯得慢慢戒掉，   要把模型当同事看，它已经完成达到这个智力水平了   。

08
##  Agent 的代数
那个两周任务到底孵出了多少个 agent？Boris 说他也不确定，估计几千到几万个。

而这是靠 dynamic workflows 来做到的：cc 用 bun 当沙箱，在里面起虚拟机，让 Claude 编排大量 agent。它不只是并行开十个 agent 那么简单，而是分阶段推进：第一批 agent 做初稿，第二批验证和汇总，第三批再度铺开……

Boris 是函数式编程出身，他给这套设计起的名字很有个人风格：   一套 agent 的代数   。有顺序执行的算子，有并行执行的算子，Claude 拿着这些算子去组合出复杂的工作。

![图片](https://mmbiz.qpic.cn/mmbiz_png/ZKqVLiaIpzFkpmQeLe4QcpCO6zIIHzvcURaJBJXAMEt1YGkpwRyWARhHzUas8tIUFZhFPficCXJp5MzS4zicxITs0iaVtrrZI7vGo6BjkAvg0dY/640?from=appmsg)

agent 编排       “    这其实是一种新形态的 test-time compute。以前说扩大推理算力，说的是多生成 token；而 dynamic workflows 是在编排推理算力，把它高效地堆到一个真正难的任务上。

另一套机制是 loops 和 routines：前者是本地跑的定时任务，后者则跑在云端。

09
##  自己维护自己
routines 玩到极致，便是这个：   现在让 Claude 维护 Claude 自己的代码库。

做法是开一个 Slack 频道，让 Claude 给 CLI、iOS、Android、桌面版各建了一堆 routine，比如：

•     清理无用代码   ：一句话的 prompt，每天跑一遍静态加动态分析，提一个 PR 删掉全部代码库里的死代码；

•     收尾实验   ：灰度已经放到 100% 的实验，自动从代码里摘除，正式上线；

•     补测试、删测试   ：给缺覆盖的地方写测试，同时删掉老模型或者前人留下的无用测试；

•     抽象警察   ：大代码库里总有几个长得差不多的抽象散落各处，它每天巡逻一遍，把这些近似重复的抽象统一掉（Boris 说这是他的最爱）。

![图片](https://mmbiz.qpic.cn/sz_mmbiz_png/ZKqVLiaIpzFnq5bk4ImTeoBUrw3Iz9ZjuJvibCE9ZyCNjB2TL0K0biboaafDFrXPiaEWGRzhI9P9WtMRBxBtQZCI6U0djLibqdQ3ev17o9JtljF0/640?from=appmsg)

抽象警察夜巡     现在这样的 routine 有二三十个，每天驱动几百上千个 agent 持续在跑。

Boris 说这在过去得是几十上百个工程师的活，而现在，工程师可以去干真正想干的事了：   做新产品，和用户聊天   。

10
##  Coding 解决了吗
Boris 之前说过「编程已经被解决了」，这次他补了个限定词：   解决的是他自己写的那类代码。

深度系统代码、分布式系统、差一个像素的 UI 验证，Claude 都还会挣扎（Opus 5 的视觉和 computer use 进步很大，但还没到完美）。

他还现场做了个举手调查：代码 100% 由 agent 写的请举手——举的人不少；超过 50% 的呢？差不多同样多。

而关于什么样的人用得最好，他的答案还是那两个字：实践。

“    忘掉你从旧模型那里学到的经验，忘掉课堂上的理论。看模型，试任务，看它在哪跌倒，然后调整。最成功的人，是那些能放下先验、愿意把失败过的想法再试一遍的人。

11
##  计算器作弊史
最后一个问题：还在读 CS 的学生，有什么该用老办法硬学的吗？

Boris 讲了自己的入行故事，这段有点点好笑。

他初中在 TI-83 计算器上学会了编程，第一门语言是 BASIC，动机非常纯粹：   在数学考试上作弊。

他写了个代数求解器，成绩上去了，还搞了根数据线把程序分发给同学，全班成绩都上去了……后来数学难到了微积分，BASIC 顶不住，他便去学了汇编，写更强的求解器，接着作弊。

![图片](https://mmbiz.qpic.cn/mmbiz_png/ZKqVLiaIpzFkue3ehjzCOzPgRiaGWeGZYFGibdwLhjqXoMTPH4hziaY01zxqgyYnTaFpbicN28EpUpEBoaGVdY5aZf2Mq5BajBqIlCMRvHlMqCico/640?from=appmsg)

计算器作弊往事     （他给 TI-83 写的编程指南，据说现在还挂在网上的某个角落。）

所以他的建议一以贯之：别只学计算机科学本身，去学怎么应用它。做产品、做创业项目、练设计感、练商业感、学数据分析、学和用户聊天。

这些技能和工程能力组合在一起，才真正的值钱。

12
##  人手一份 Max 20x
访谈结尾，Boris 给现场所有人发了 Max 20x 订阅，Diana Hu 则补充道：

“    这个房间里应该有人去做那种一跑好几个月、驱动几千个 agent 的东西了，现在你们有额度了。

当然，对于没买票的正在读这篇文章的你来说……额度是没有的，但方法全在上面了，希望对你的帮助不止一个 Max。
