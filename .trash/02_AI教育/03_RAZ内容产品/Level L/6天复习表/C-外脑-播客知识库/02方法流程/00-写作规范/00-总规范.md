# 02 方法流程 总规范（三前缀分类）

> **优先级**：这是 `02方法流程/` 下所有笔记（含 `_stubs/`）的**顶层规范**。三份子规范（SOP / 框架 / 心法）在本规范之下细化各自骨架。
>
> **立规缘起**：2026-07-13。用户先立了《00-SOP写作规范.md》强调"02 是可直接使用的操作手册"；同日又指出 02 里其实混着多种物种，硬套 SOP 骨架会写坏其中一部分。本规范据此把 02 层拆成三种前缀，各按各的规范。

---

## 一、02 层的三种物种

| 前缀 | 物种 | 回答的问题 | 使用姿势 | 对应规范 |
|---|---|---|---|---|
| `[SOP]` | 操作手册 | **"我第一步做什么？"** | 打开文件，按 Step 1→N 打勾执行 | `01-SOP写作规范.md`（沿用原《00-SOP写作规范.md》） |
| `[框架]` | 判断工具 / 评估模型 | **"这个东西/人/机会到底怎么样？"** | 用维度和观测信号打分或分级 | `02-框架写作规范.md` |
| `[心法]` | 行动准则 / 单点原则 | **"我在什么场景要想起它？"** | 决策前扫一眼，防止踩坑 / 走错路 | `03-心法写作规范.md` |

### 三者的本质区别

- **SOP** 是一条**时间轴**：过程有先后，可以打勾。
- **框架** 是一张**表格**：维度并列，一次评估打完分。
- **心法** 是一个**信号灯**：单点提醒，命中就用。

## 二、分类判据（新建或分类 stub 时按此判断）

按顺序问 3 个问题，第一个"是"决定归属：

### 问题 1：这个方法有明确的先后步骤吗？

- **有**（Step 1→2→3→4，做完 A 才能做 B）→ **`[SOP]`**
- 没有 → 进问题 2

### 问题 2：这个方法核心是"评估/判断/选择"吗？

- **是**（用维度评分、用信号观测、用分级选路径、if-then 决策）→ **`[框架]`**
- 不是 → 进问题 3

### 问题 3：这个方法本质是一条原则/提醒/戒律吗？

- **是**（几句话讲完，靠场景触发想起来）→ **`[心法]`**
- 都不像 → **不属于 02**，检查是不是应该挪到：
  - `03概念链接/`（讲的是"X 是什么" / "X vs Y"）
  - `01人物原萃/`（讲的是某人的一整套心智模型）
  - `04判断哲学/`（具体决策节点的取舍理由）
  - `05深度研究/`（跨集合成的深度主题）

### 补充判据：混合形态怎么办

- **框架 + SOP**：像"生命力四维度评估模型"这种"有 4 维度打分 + 有评估流程"的——**主属性看哪个占篇幅 60% 以上**。评估维度是主体、流程只是配套 → `[框架]`；流程是主体、维度只是打分卡 → `[SOP]`。
- **心法 + 框架**：像"论迹不论心复盘法"，既是原则又想给出打分——**先看它是不是能几句话讲完，能→`[心法]`，写不长；不能→`[框架]`**。
- **拿不准**：先归入 `_stubs/` 用 `[?]` 前缀（如 `[?] 神不外驰使用时机.md`），等到有第二个来源出现再决定升级到哪个前缀。

## 三、目录组织

```
02方法流程/
├── 00-写作规范/                # 元规范目录（本目录）
│   ├── 00-总规范.md             # 本文件
│   ├── 01-SOP写作规范.md        # SOP 类骨架（沿用旧 00-SOP写作规范.md，内容不变）
│   ├── 02-框架写作规范.md       # 框架/评估模型类骨架
│   └── 03-心法写作规范.md       # 心法/原则类骨架
├── [SOP] xxx.md                # 合格 SOP 成品
├── [框架] xxx.md               # 合格框架成品
├── [心法] xxx.md               # 合格心法成品
└── _stubs/
    ├── [SOP] xxx.md            # 待返工 SOP
    ├── [框架] xxx.md
    ├── [心法] xxx.md
    └── [?] xxx.md              # 尚未分类
```

**注意**：
- 前缀写在文件名头部，用方括号包裹，与主标题之间空一格。
- Obsidian 中 wiki link 引用时可以直接写 `[[方法名]]`（不含前缀）——通过 `aliases` 字段做别名映射。
- 旧文件《00-SOP写作规范.md》**保留原位不动**，同时把它复制到 `00-写作规范/01-SOP写作规范.md`；未来只维护新副本，旧文件加"已迁移，见 00-写作规范/"提示。

## 五、通用红线（三类都要遵守）

1. ❌ **禁止在正文里做人物/来源引用夹叙夹议** — 来源统一放底部 `## 来源` 节。
2. ❌ **禁止把"为什么值得学"作为开篇** — 想写背景，一律放到最后 `## 附录：为什么值得用`。
3. ❌ **`## 一句话` 章节 ≤ 40 字，且不含"某某说 / 某某提出"字样**。
4. ❌ **附录不得超过主体篇幅**。
5. ❌ **返工前必须完整读一遍原文；返工不得删除原素材**。这是**最强红线**。
   - 原 stub 已提炼的**原话、案例、类比、推演示例、来源、关联链接**必须**全部保留**，只允许换位置（挪到附录 / 折叠区 / 关联区），不允许因为"新骨架里没这一节"就删掉。
   - 如果新骨架容纳不下原素材，追加 `## 附录：原文素材` 章节兜底，把无处安放的段落原样保留在里面。
   - 违反这条 = 违反用户 2026-07-13 明确纠正："重新写的话，记得回顾一下原文的内容"。

各类还有自己的红线，见子规范。

## 六、维护与演化

- 三类**并存不合并**：不试图用统一骨架框住三类，硬合并会退化成 v0（今天用户已明确纠正过的形态）。
- 三类之间可以互链：
  - `[框架]` 里的某个"打分完 → 采取的行动"可以链到 `[SOP]`。
  - `[心法]` 里的"什么时候用" 可以链到具体的 `[框架]` 或 `[SOP]`。
- 每季度审计 stub 前缀分布：如果某一类只有个位数 stub，考虑并入邻类；如果某一类超过 60 个 stub 且长期停留在 stub 状态，说明骨架规范可能过重，需要精简。
