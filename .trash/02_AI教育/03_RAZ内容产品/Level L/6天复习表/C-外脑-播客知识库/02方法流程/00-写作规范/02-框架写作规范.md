# 02 方法流程 · 框架写作规范（`[框架]` 前缀专用）

> **适用范围**：本规范专管 `02方法流程/` 下前缀为 `[框架]` 的笔记。用户拿到具体人/项目/机会/产品，需要**评估、判断、分级、选路径**时打开这类文件。
> 顶层入口见 [[00-总规范]]。
> 立规缘起：2026-07-13。SOP 骨架强调"Step 1→N 打勾"，但评估框架的核心不是流程而是**维度和信号**，强套 SOP 会写坏——故拆出本规范。

---

## 一、框架的本质定义

**框架 =「一张评估表 + 对应的判断规则」**，回答"这个东西到底怎么样 / 该选哪条路"。

判断某个笔记是否属于 `[框架]`：

> **看到这份笔记，用户能不能对着眼前的一个具体对象（一个人、一个项目、一次机会）当场打分或选路径？**

- ✅ 能 → 是合格的 `[框架]`
- ❌ 不能（只是解释"XX 是什么" / "XX 为什么重要"）→ 应挪到 03 概念链接

**与 SOP 的区别**：SOP 讲"先做 A 再做 B 再做 C"，框架讲"看 A 维度 + 看 B 维度 + 看 C 维度，一起决定结论"。**SOP 是时间序，框架是空间并列。**

---

## 二、框架与"概念解释"的辨别清单

| 特征 | 合格 `[框架]`（02） | 不合格（伪装成框架的概念） |
|---|---|---|
| 开头 3 行 | 直接给出维度清单和评估目标 | 讲这个概念的历史/为什么被提出 |
| 主体 | 维度定义 + 每个维度的**观测信号表**（好/坏两栏） | 一段段散文式论述"什么是韧性" |
| 可复用产物 | 有**打分卡 / 分级表 / 决策树**可以直接抄 | 没有任何可以填的表 |
| 判断结果 | 明确写"打完分怎么用"——高分→X，低分→Y | 结论开放，让用户自己悟 |
| 篇幅分布 | 维度+观测信号+打分卡 > 60%，其余 < 30% | 定义/理论 占大头 |
| 来源引用 | 只在底部 `## 来源` | 正文里反复出现"XX 说" |

**红线判据**：如果一份 `[框架]` 里没有可以对着眼前对象**当场打分或分级**的表格，直接判定不合格。

## 三、标准骨架（模板）

新建或返工 `[框架]` 必须使用以下骨架：

```markdown
---
tags: [方法, 框架, ...]
created: YYYY-MM-DD
layer: extract
status: stub / growing / stable
provenance: external / mixed
viewpoint_owner: external_author / mixed
prefix_type: 框架
framework_type: 评估模型 / 分级模型 / 决策树 / 判断矩阵 / 分类框架
dimensions: [维度1, 维度2, 维度3, ...]      # ← 框架专属：并列维度
aliases: [...]
source_count: 1
sources:
  - show: "..."
    episode: "..."
    speaker: "..."
---

# [框架] <框架名>

## 一句话（≤ 40 字）
评估什么对象 + 用几个维度 + 得到什么结论。不写来自谁。

## 什么时候用（触发条件，3-5 条 bullet）
- 场景 A（例如："第一次接触一个陌生创业者，5 分钟内要初判"）
- 场景 B
- **红线**：不适用于 X 场景

## 评估对象（这个框架用来打分的是什么）
- 人 / 项目 / 产品 / 机会 / ...
- 具体到什么颗粒度

## 维度定义（框架的骨）
（每个维度独立成小节，并列关系）

### 维度 1：<维度名>——<一句话操作定义>

**观测信号**：

| ✅ 好信号（这方面强） | ❌ 坏信号（这方面弱） |
|---|---|
| 具体行为 1 | 具体行为 1 |
| 具体行为 2 | 具体行为 2 |
| 具体行为 3 | 具体行为 3 |

→ **怎么问出来 / 怎么观察出来**：一句话给出触发问题或观察方法。

### 维度 2：...

（维度 3-6 个为宜；再多考虑合并；再少考虑并入其他框架）

## 打分卡 / 分级表（可复制粘贴）

给出可以直接抠走的评估工具：

| 对象 | 维度1 | 维度2 | 维度3 | 维度4 | 综合结论 |
|---|---|---|---|---|---|
| A | ⭐⭐⭐ | ⭐⭐ | ⭐⭐⭐⭐ | ⭐ | ... |

或分级：

- **A 级**：维度 1-3 全高 → 建议 X
- **B 级**：维度 1 高，其余中等 → 建议 Y
- **C 级**：多个维度低 → 建议 Z

## 打完分怎么用（决策后果）

- 若得分 X → 采取行动 A（可链到 [[某个 SOP]]）
- 若得分 Y → 采取行动 B
- 若打不出分 → 说明输入信息不足，先补齐 X

## 常见坑（3-5 条）

- ❌ 不要把某一维度当唯一决定因素（原因 1 行以内）
- ❌ 不要用框架给出宿命论结论（框架是决策辅助，不是判决书）
- ❌ 不要在维度之间强行合并

## 附录：实例（1 个跑通的例子）

对一个具体对象（可以匿名）完整跑完打分，说明结论如何得出。**不塞进维度定义章节**。

## 来源

- [[89单集笔记/... | XXX]] — 一次引用取的是什么 [原话 / 归纳]

---

> stub：X 个来源。跨节目再次出现时升级到父目录。
```

## 四、写作红线（禁止清单）

1. ❌ **禁止把维度写成"很重要 / 需要注意"式散文** — 每个维度必须有观测信号表。
2. ❌ **禁止只列维度不给打分卡** — 没有打分卡的框架 = 概念解释。
3. ❌ **禁止把 SOP 混进框架** — 需要"先做 A 再做 B"的评估流程，把流程拆到附录或另建 `[SOP]`。
4. ❌ **禁止用同一份笔记同时评估 3 类以上不同对象** — 一个框架只服务一类对象。
5. ❌ **禁止维度定义超过 5 行没有信号表就断句** — 一行操作定义 + 立即上表。
6. ❌ **禁止"打完分怎么用"这一节写成开放式** — 至少给出 2-3 条明确行动。

## 五、自检清单（提交前必过 7 关）

- [ ] **对象判据**：明确写出评估对象是什么（人/项目/产品/机会/...）？
- [ ] **维度并列判据**：3-6 个维度是并列关系，不是时间先后？
- [ ] **信号表判据**：每个维度都有好信号 / 坏信号对照表？
- [ ] **打分卡判据**：有可以直接抠走的打分卡 / 分级表 / 决策树？
- [ ] **行动判据**：写清了"打完分怎么用"？
- [ ] **背景占比判据**：背景/来源/定义合计篇幅 < 30%？
- [ ] **一句话判据**：`## 一句话` ≤ 40 字，且不含"某某说 / 某某提出"？

## 六、返工原则

- **返工前必读原文**（强红线）：动手前必须先完整读一遍原 stub，识别其中的原话、案例、类比、推演示例、来源、关联链接，逐项决定新骨架里怎么安放。**禁止不读原文就按新骨架重写**——会丢失已提炼素材。
- 已存在的 stub 若被分类为 `[框架]` 但不符合规范：**不删除**，**改写骨架**——把原文里的方法论描述保留到附录，主体按新骨架重写。原文中的推演示例、案例、类比无处安放时，追加 `## 附录：原文素材` 兜底。
- 单次批量返工上限：**10 个 stub / 批次**。
- frontmatter 追加 `revised_at: YYYY-MM-DD` 和 `revised_reason: "对齐 框架 规范 v1"`。

## 七、示例与反例

### 正例（合格 `[框架]`）

`[框架] 生命力四维度评估模型.md`（已存在，2026-07-11 版本）：
- ✅ 4 个维度并列（韧性/定力/自我净化/自我突破）
- ✅ 每个维度有"好信号 vs 危险信号"表
- ✅ 每个维度末尾有"怎么问出来 / 怎么观察出来"
- ✅ 来源只在底部
- ⚠️ **待补**：明确的打分卡（当前是维度定义，缺少综合打分与"打完分怎么用"）→ 从 growing 升到 stable 前需要补齐

### 反例（伪装成框架的概念）

某"AI Native 半步退"如果写成"什么是 AI Native / 为什么半步退才对 / 案例"——就是概念解释，应归 03。要让它进 02[框架]，必须能给出"评估一个产品是不是 AI Native"的打分表。

## 八、与其他前缀的边界

- **`[SOP]`**："我第一步做什么" → 时间序步骤 → 用 SOP 规范
- **`[框架]`**："这个东西怎么样 / 该选哪条路" → 空间并列维度 + 打分 → 用本规范
- **`[心法]`**："我在什么场景要想起它" → 单点原则，几句话讲完 → 用心法规范

**判据关键词**：

- "打几分 / 分几级 / 好/坏信号 / 走哪条路" → `[框架]`
- "先做什么再做什么" → `[SOP]`
- "别忘了 / 提醒自己" → `[心法]`
