# AI Native 研发工作流

## 一句话

重构研发流程的核心原则：默认让 AI 承担全流程（文档、测试、设计、代码、review、监控），人只在 AI 暂时做不到的环节补足上下文、判断与责任。

## 怎么用

### Step 1：列出研发链路上的所有环节

写下来从 idea 到上线你团队实际经过的所有步骤。典型环节包括：需求文档 → 设计说明 → 代码生成 → 单元测试 → Code Review → 集成测试 → 部署 → 监控告警。每个环节问一个问题：这个环节有没有清晰 SOP？如果有，优先让 AI 做。

### Step 2：为每个环节找到 AI 工具/流程

| 环节 | AI 化方式 | 人介入条件 |
|---|---|---|
| 需求文档 | AI 从对话/Linear 任务生成文档 | 需要行业知识、客户洞察时人补充 context |
| 设计说明 | AI 生成 UI/交互草案 | 设计师在 60 分基础上优化到 80-100 分 |
| 代码生成 | Claude Code / Devin 自动生成 | 复杂架构决策、核心基础设施改动 |
| 单元测试 | AI 自动生成覆盖 | 关键路径人审 |
| Code Review | AI review（10 分钟级） | 基础设施、数据相关、高风险改动 |
| 部署 | CI/CD + AI 检查 | 异常时人介入 |
| 监控 | Incident.io 聚合分析 | 人处理复杂故障根因 |

### Step 3：缩短反馈周期，重构风险管理

传统 code review 1-2 天 → AI review 10 分钟。风险管理逻辑从「review 阶段拦截所有问题」转为「快速上线 + 快速发现问题 + 快速 revert/修复」。前提是可快速回滚的架构。

## 配套原则：减少人与人同步

（不是步骤，是运行前提。人与人之间的同步是 AI 工作流的第一瓶颈。）

- 尽量让一个人独立和 AI 完成端到端工作
- 将规则、原则和上下文沉淀到 codebase 或文档，让 AI 自动读取
- 日常会议集中在 3-4 小时窗口，其余时间不安排会议

## 完整示例

以 Palona AI 的餐馆电话 Agent 的产品迭代为例：

1. **需求输入**：工程师直接见餐饮老板，获取反馈（"客户希望在接电话时能识别回头客"）
2. **文档生成**：将对话要点输入 Claude Code，生成需求文档初稿
3. **设计**：AI 生成交互草案，设计师在已有版本基础上优化
4. **代码生成**：创建 Linear 任务，Devin 自动生成后端和前端代码
5. **Code Review**：AI review 通过后可 merge，约 10 分钟
6. **上线**：CI/CD 自动部署
7. **监控**：Incident.io 实时监控异常，发现错误立即 revert

## 适用场景与边界

- **适用**：创业公司（<50 人）、产品快速迭代阶段、有清晰 SOP 的环节、可快速回滚的架构
- **不适用**：基础设施/核心安全/数据相关的关键改动（仍需要人审）、大公司受制于组织惯性难以全面推进
- **已知局限**：依赖高质量的上下文工程（人必须提供准确、高信噪比的 context），对复杂历史代码需要人整理边界条件和约束
