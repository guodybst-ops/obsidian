# 工程先做60分版本迭代法

## 一句话

创业团队应该由工程团队借助 AI 先做出可上线的 60 分产品版本，再由设计、产品等角色优化到 80-100 分。因为 AI 让 coding 成本极低，先做再对齐的成本远低于长时间会议对齐。

## 怎么用

### Step 1：工程团队直接用 AI 做出可上线版本

前提：产品方向已大致清晰，不需要完美设计稿。

工程团队拿到需求后：
- 用 AI（Claude Code/Devin 等）生成代码
- 目标：功能完整、可上线、可用——不要求美感、不要求极致体验
- 时间：尽可能快（1-3 天）

### Step 2：上线后基于真实版本对齐

关键转变：过去是先设计讨论几周 → 再开发几周 → 上线。现在是先上线 60 分版本 → 在真实产品和真实用户反馈面前对齐。

因为真实产品比 mockup/设计稿/文档更能激发有效讨论：
- 设计师看到真实产品后，能更好地提出改进方向
- 产品经理看到真实用户反馈后，能更好地调整优先级
- 市场团队在真实产品上做 GTM 准备，更有效率

### Step 3：设计师和产品在 60 分基础上优化

设计师不是消失了，而是从"先画图"变成"在真实产品上优化"：
- 视觉和交互从 60 分提升到 80 分
- 动效、微交互从 80 分提升到 90 分
- 品牌体验和情感设计从 90 分提升到 100 分

### Step 4：判断什么时候不能只做 60 分

- 涉及品牌调性的核心体验（如首页、onboarding）→ 不能太差
- 涉及用户安全/信任的功能（如支付、隐私设置）→ 必须高于 60 分
- 竞品已经做到 90 分的领域 → 60 分不够，需要至少做到 80 分才能上线

## 完整示例

以 Palona AI 的餐馆电话 Agent 为例：
1. 需求：让 Agent 能识别回头客（客人第二次打电话时能叫出名字、记得上次的订单）
2. 工程师不写详细设计文档，直接用 Claude Code + Agent 框架生成第一个版本
3. 1 天后，60 分版本上线测试环境——功能可用但体验粗糙（回复延迟 1 秒、问候语不够自然）
4. 设计师加入：优化问候语的语气、设计来电识别的声音提示
5. 1 周后，版本从 60 分优化到 85 分，上线生产环境
6. 用户反馈："你们的 AI 居然记得我上次点过什么，太神奇了"

## 适用场景与边界

- **适用**：AI 创业公司、快速迭代阶段、团队 < 50 人、to C 或 to SMB 产品
- **不适用**：企业级基础设施、医疗/金融等严格合规产品、核心安全功能
- **已知局限**：不适合已经有大规模用户的成熟产品（用户体验回退可能引起流失）
